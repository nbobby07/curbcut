## Repair families shipped

### Tier A — shipped

1. Missing form label (`label`)
   - Native `input`, `select`, and `textarea` only.
   - Requires human-provided visible text, 1–120 visible characters.

## Deterministic repair engine

`src/repairs.ts` is a three-family dispatcher. It returns either a validated patch set or an explicit refusal code. There is no generic rewrite function and no AST serialization.

Every patch has:

```ts
{
  start: number
  end: number
  expectedText: string
  replacement: string
}
```

The existing M1 `applySourcePatches` primitive validates integer bounds, exact `expectedText`, overlap/duplicate ranges, and applies from the highest offset downward. Proposed HTML is reparsed with parse5, checked for new parse errors, and checked for the family-specific structural result. Canonical source is never generated by serializing the AST.

## Proposal lifecycle and approval

One proposal can be pending at a time:

`PROPOSED → APPROVED → APPLIED`

or:

`PROPOSED/APPROVED → REJECTED`

A proposal stores the issue/scan/revision identities, mapped node/range, original SHA-256 HTML/CSS hashes, exact patches, proposed HTML/CSS, compact diff, classification, rationale, expected axe validation, semantic values, approval, SHA-256 diff binding, and apply/restoration targets.

Approval is a visible UI action labeled **Approve this exact change**. It records:

- actor `human`;
- proposal ID;
- exact diff hash;
- approval timestamp.

Apply is disabled before approval. Apply recomputes the working-source hashes and the diff binding, checks proposal/revision/approval identity, reruns the guarded patches, compares their result to the reviewed proposed source, reparses the result, then commits atomically. The diff binding covers exact patches, proposed HTML/CSS, human values, and the apply/restoration validation targets.

Manual HTML or CSS edits invalidate a pending proposal. Changing a semantic answer requires rejecting and generating a new unapproved proposal/diff.

## Byte-preservation and exact Undo evidence

- M1 raw-patch tests still assert every byte outside patches is preserved.
- M3 repair tests cover CRLF, Unicode, quote style, attribute order, similar neighboring nodes, and untouched surrounding bytes.
- Proposal creation tests assert canonical HTML/CSS remain unchanged.
- Apply tests assert the exact intended replacement rather than a normalized/serialized document.
- Undo compares current SHA-256 hashes and exact strings to the latest after-state before restoring exact before-state HTML/CSS.
- Manual edits after Apply produce `STALE_UNDO` rather than overwriting user work.
- History is in-memory, linear, latest-only for Undo, and capped at 20 records.

Browser form controls normalize CRLF entered through Playwright `fill` to LF. Raw CRLF preservation is therefore asserted in the parser/repair unit tests; browser Undo is asserted against the exact canonical string the browser actually stored.

### DOMPurify/axe tabindex discrepancy

DOMPurify `3.4.14` removes positive `tabindex` in this browser even when it appears in the explicit allow-list. axe-core marks `tabindex` as a disabled-by-default best-practice rule, so M2's default `axe.run(document)` also did not report it.

M3 enables only the named axe rule and, after DOMPurify completes, restores only a parse5-mapped value matching `^[+-]?[0-9]+$`. `autofocus` remains forbidden and event handlers/scripts remain removed. Real Chrome evidence then showed `tabindex` serious before repair, absent after repair, and restored after Undo. The primary fixture remains unchanged because it contains no positive tabindex.

## Deviations

1. Tier B was deliberately cut under the approved scope rule.
2. The axe `tabindex` rule had to be explicitly enabled because axe-core `4.13.0` ships it disabled by default.
3. DOMPurify's focus-trigger hardening required the narrow validated tabindex restoration described above; this strengthened the boundary by explicitly forbidding `autofocus`.
4. Playwright `1.62.1` was added and pinned because M3 explicitly requires durable browser/E2E regression coverage.
5. The obsolete spike repair implementation was removed so there is only one production repair model and no misleading DOM-serialization helper.

## Known limitations

- The workspace and 20-entry history are memory-only and reset on reload.
- Undo supports only the latest eligible change; no redo or branching history.
- Verification targets use a literal generated/existing ID for label or a revision-remapped node ordinal for attribute-only image/tabindex repairs. Dynamic DOM and JavaScript are unsupported by design.
- Human semantic text is syntactically validated, not judged for quality.
- CSS remains sanitized by the M2 execution boundary/CSP rather than a full CSS parser. CSP blocks external responses, but browser tooling can still observe blocked URL attempts.
- Proposed preview uses the same opaque controller and sandbox, but the UI displays the working frame's isolation evidence rather than maintaining a second diagnostics record.
- The axe bundle keeps the main Vite chunk above 500 kB; optimization is deferred.
- No Tier B repairs, export tool, persistence, M4 WebMCP mutation tools, final timeline, or final eval suite were added.

## Top three remaining technical risks

1. **Sanitizer/CSP/browser drift.** DOMPurify's tabindex behavior changed unexpectedly; other browser or sanitizer changes could alter audit fidelity or blocked-network observability. The security/E2E matrix must remain a release gate.
2. **Target equivalence after more complex edits.** M3's ID/ordinal validation is sound for these surgical families, but future repairs that insert/remove multiple neighboring nodes need stronger cross-revision identity evidence.
3. **M4 WebMCP approval integrity and sequencing.** The browser agent must be able to preview/reject/undo through structured tools without gaining a silent semantic-approval or Apply bypass. State-machine and multi-prompt eval quality remain the largest next milestone risk.

## Recommendation

**PROCEED TO M4** — only after review of this report. Do not weaken the human approval boundary, sanitizer/CSP regression suite, or target-scoped real-axe verification when exposing the remaining WebMCP workflow.
